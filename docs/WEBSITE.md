# Azuria website

The website source is stored in `website/` in the launcher repository. It is a small static product site with Home, Downloads, Changelog, Help, Privacy policy, Terms of service and Contact pages, plus a 404 page. It uses built-in Node.js APIs and has no package dependencies, database, website accounts, remote font requests, analytics or advertising scripts. The only browser API request checks GitHub for the latest published release.

## Build and review

Use Node.js 24. No dependency installation is required for the website.

```sh
npm --prefix website run build
npm --prefix website test
npm --prefix website run preview
```

Open `http://127.0.0.1:8080/azuria-launcher/`. The local preview server mounts the built site at the same path as the intended GitHub Pages project site. Build output is written to `website/dist/` and ignored by Git. Stop the preview with Ctrl+C.

The website workflow checks links, fragments, metadata, release-content escaping, download destinations and the launcher-release exclusion rule. It uploads an `azuria-website` build artifact for review. Mobile navigation, appearance screenshot switching and native FAQ disclosure controls are implemented; browser visual and interaction QA remains required before public hosting.

## Release information

`website/data/releases.json` is a checked-in snapshot of real published GitHub releases. It is used for local and offline builds, not hand-written marketing statistics.

```sh
npm --prefix website run refresh
npm --prefix website run build
```

The refresh command reads this repository's public GitHub release API. It optionally uses `GH_TOKEN` from the environment; no token is written into the generated site. It rejects an unsuccessful response instead of silently generating broken download links. Published installer URLs are validated to belong to this repository. Release-note text is escaped and rendered as basic headings, lists and paragraphs; arbitrary HTML is never included.

CI refreshes metadata before each website build using GitHub’s `/releases/latest` endpoint as the authoritative first entry, followed by release history. A six-hour scheduled build is a fallback for manual releases or edited notes. After publishing an app release, the existing release workflow explicitly dispatches the website workflow. This avoids relying on a release event generated by `GITHUB_TOKEN` to start another workflow. The browser also checks the public latest-release API on page load, every 15 minutes while visible, and after returning to a tab that has been idle for five minutes. It validates repository, release state, tag and URLs before updating the latest version, date, leading release card and changelog. Release text is inserted as text, never HTML. API failures leave built information visible with an explicit fallback message. All primary download controls fall back to the stable GitHub `releases/latest` page, so a stale or offline page does not offer an outdated installer URL. A successful live check upgrades those controls to the validated current Windows installer for a direct download. No version number needs to be edited in the website source for each release. Website dispatch is a non-blocking step after app publication; if it fails, rerun the website workflow without republishing the installer.

Website-only edits are ignored by the app workflow where possible. A separate release-scope check also prevents website/documentation/CI-only commits from publishing an installer. Changes to launcher source or `docs/RELEASE_NOTES.md` still permit the existing release process. Unknown paths conservatively count as launcher-relevant changes.

## Public hosting

The GitHub Pages deployment workflow targets:

`https://jamesb123450.github.io/azuria-launcher/`

A repository administrator must select **Settings → Pages → Build and deployment → Source → GitHub Actions** before the first deployment can succeed. The connected GitHub App cannot change this administrative setting. Once enabled, run **Website build and deploy** from the Actions tab on `main`, or rerun the failed deployment.

The workflow builds and tests the site, uploads a Pages artifact, and deploys only `main` through the `github-pages` environment. Pull requests and feature branches produce review artifacts without deploying. App releases dispatch the same workflow to refresh the public download and changelog pages.

After the first deployment, verify the live pages, mobile navigation, appearance controls, download link and project-path assets. Local browser visual and interaction QA has not yet been completed.

The build defaults to the proposed project-site URL. Set `AZURIA_SITE_URL` to an HTTPS URL ending in `/` when using a custom domain; the build derives links, canonical URLs, social metadata and sitemap paths from that value. The local preview helper is for the default `/azuria-launcher/` path.

Installers remain hosted on GitHub Releases. GitHub Pages serves only website files. A custom domain is optional and has not been purchased or configured.

Keep current capabilities separate from development plans. The website does not display the fictional Discover catalogue or made-up projects/statistics. Existing launcher screenshots use sample instance configurations to demonstrate real UI controls. Game installation and launching are unavailable; Minecraft Services application access is pending review. Discover screenshots show fictional catalogue examples. Do not advertise these as functioning integrations.

Screenshots in `website/assets/` are actual local launcher interface captures using example instances, with no account credentials or personal data. The light appearance preview shows an empty library. The supplied Azuria icon is reused from the app. Inter is self-hosted with its licence included in `website/assets/INTER-LICENSE.txt`. Source, author, licence and modifications are credited in the public footer and `website/assets/MINECRAFT-CREDIT.txt`. It is not gameplay captured in Azuria. Release cards use actual published releases. Lunar Client’s homepage informed that hierarchy; its artwork, wording, statistics and product claims are not reused. The original geometric SVG is retained only for decorative release-card artwork. The structure uses concrete product screenshots, clear download guidance, real release history and direct development disclosures. ## Privacy and trust

Privacy and terms pages describe the actual site and development build without claiming legal certification or excluding statutory rights. The maintainer is identified by the public GitHub account; no company address, private inbox or response time is invented. Contact uses working GitHub issue links, with a clear public-data notice and no message-collection form. No website accounts or sign-in forms are provided. GitHub processes hosting and download requests under its own policies. Website styling, JavaScript, fonts and screenshots are served locally, with a restrictive content security policy. No account credentials, signing keys or API secrets are included in website assets.

Update signatures and Windows Authenticode signing are different mechanisms. Describe development installers accurately rather than claiming Microsoft verification or a trusted Windows publisher. The source is public, but the project does not yet have a selected licence; use “view source” rather than claiming an open-source licence.
